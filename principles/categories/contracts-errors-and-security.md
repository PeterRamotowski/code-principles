# Contracts, Errors, Validation, and Security

This category groups related concepts for navigation. Category membership does not make every item equally normative.

| Entry | Classification | Summary |
|---|---|---|
| [Defensive Programming](../compendium/defensive-programming.md) | `technique` | Anticipate invalid input, partial failure, and misuse at relevant boundaries. |
| [Design by Contract](../compendium/design-by-contract.md) | `method` | Specify preconditions, postconditions, and invariants for operations and types. |
| [Fail Fast](../compendium/fail-fast.md) | `principle` | Detect and report invalid conditions close to their source. |
| [Make Illegal States Unrepresentable](../compendium/make-illegal-states-unrepresentable.md) | `principle` | Use types and constructors that prevent invalid combinations where practical. |
| [Parse, Don’t Validate](../compendium/parse-dont-validate.md) | `principle` | Transform untrusted input into types that represent validated meaning. |
| [Postel’s Law / Robustness Principle](../compendium/postels-law.md) | `heuristic` | Historically: be conservative in output and liberal in accepted input; modern use requires caution. |
| [Principle of Least Privilege](../compendium/principle-of-least-privilege.md) | `security-principle` | Grant only the permissions and capabilities required for the task. |
